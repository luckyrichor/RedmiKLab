# 主动测速调度与蜂窝网络诊断加固

## 目标

针对 K60 夜间报告中主动测速闹钟约 1 分 40 秒的启动延迟，以及测速失败时缺少蜂窝候选网络和系统能力证据的问题，增强严格模式测速调度和报告诊断能力。同一 APK 继续兼容 K60 与 K80。

## 已确认根因

1. 严格模式快照、检查点和结束动作已经由持有唤醒锁的连接级采集服务按绝对时刻触发，但主动测速仍只由 `AlarmManager` 触发。小米系统在锁屏或休眠时延后交付测速闹钟，形成约 1 分 40 秒的启动延迟。
2. 当前蜂窝解析器只返回最终 `Network` 或空值。失败报告不能回答当时系统发现了哪些网络、默认网络是不是 VPN、蜂窝候选具备哪些能力、网络请求是超时还是异常，以及最终为何没有选择网络。
3. 内部严格调度与系统闹钟作为双通道同时存在时，主动测速没有按计划时刻去重，可能重复消耗流量。

## 方案

### 蜂窝网络候选与系统能力诊断

- 每次测速尝试都记录解析前和解析后的网络状态。
- 记录系统默认网络、全部可见网络及每个网络的传输类型和关键能力：蜂窝、VPN、Wi-Fi、Internet、Validated、Not Suspended、Not Restricted、Metered。
- 记录蜂窝网络请求结果：直接命中现有候选、回调取得候选、等待超时、权限或运行时异常。
- 记录最终选中的网络和选择理由；没有候选时明确写入失败原因。
- 诊断数据使用已有 `diagnostic_events` 保存，并通过 `diagnostic_events.csv` 导出，不新增敏感数据或网络正文。

### 严格模式主动测速内部调度

- 严格模式连接级采集服务根据诊断开始时间和吞吐间隔，按绝对计划时刻安排主动测速。
- 内部调度使用现有有上限的 CPU 唤醒锁和 Handler 绝对时刻机制，不从上一轮执行结束时刻累加，避免漂移。
- 系统精确闹钟继续保留，作为进程、VPN 服务或内部调度异常后的恢复后备。
- 标准模式保持现有系统闹钟调度方式。

### 测速去重与延迟记录

- `probes` 增加计划时刻、调度延迟和触发来源字段。
- 同一 Run ID 和计划时刻只执行一轮测速；内部调度或系统闹钟中先到的一方执行，后到的一方被忽略。
- 报告的 `probes.csv` 显示计划时刻、实际启动时刻、延迟和触发来源，便于验证优化结果。

## 测试与验收

- 单元测试覆盖默认网络为 VPN、存在多个蜂窝候选、未验证候选、请求超时和异常诊断。
- 单元测试覆盖严格模式在吞吐计划时刻发出测速动作、恢复后跳过过期时刻以及任务耗时不累积漂移。
- DAO 测试覆盖按 Run ID 和计划时刻查询测速记录及数据库 11→12 迁移。
- 报告测试覆盖新增测速计划、延迟和触发来源列，并确认网络诊断事件随 ZIP 导出。
- 运行全量单元测试、Android Lint、Debug APK 构建；安装到当前连接的 K80 并验证启动和数据库迁移。

## 边界

- 不能承诺 Android 系统硬实时，但严格模式将不再以厂商闹钟交付作为主动测速的唯一入口。
- 不改变主备测速地址、5+5 次重试、10 秒间隔、单次 5 MB 和每晚 1 GB 预算。
- 不保存数据包正文、账号凭证或下载内容。
